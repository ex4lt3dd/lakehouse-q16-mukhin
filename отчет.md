### Скрипты, которыми поднимал стек

Конфиг — [docker-compose.yml](docker-compose.yml), каталоги — [catalog](catalog/), запуск — [scripts/start.ps1](scripts/start.ps1). Проект `mukhin-q16` использует отдельную сеть и тома. Версии образов закреплены digest. Пароли генерируются в локальный `.env`.

Запуск из папки проекта в PowerShell:

```powershell
# Генерация .env, запуск Silo/PostgreSQL, миграций Lakekeeper,
# Lakekeeper/Trino, создание трёх бакетов и warehouse; сборка и запуск Superset.
./scripts/start.ps1 -Python python

# Контейнеры и каталоги.
docker ps --format '{{.Names}} | {{.Image}} | {{.Status}} | {{.Ports}}'
docker compose exec -T trino trino --execute 'SHOW CATALOGS'
```

Основные команды внутри `start.ps1`:

```powershell
# Сервисы и одноразовые jobs миграций/создания бакетов.
docker compose --progress quiet up -d minio postgres migrate lakekeeper buckets trino
# Bootstrap и warehouse bronze/silver/gold через management REST API.
python -X utf8 scripts/lab.py provision
# BI с установленным драйвером Trino.
docker compose --progress quiet up -d --build superset
```

У S3 console host-порт `19001`, потому что `9001` был занят. S3 API — `9000`, Lakekeeper — `8181`, Trino — `8080`, Superset — `8088`. Связь между контейнерами идёт по именам `minio`, `postgres`, `lakekeeper`, `trino` внутри Compose network; `localhost` внутри контейнера для соседнего сервиса не используется.

## 3\. Разбор запроса — какие данные нужны

| Таблица TPC-H | Колонки | Использование в запросе |
| :---- | :---- | :---- |
| `part` | `partkey`, `brand`, `type`, `size` | partkey — join с partsupp; brand <> 'Brand#45'; type NOT LIKE 'MEDIUM POLISHED%'; size IN (49, 14, 23, 45, 19, 3, 36, 9). brand/type/size участвуют в GROUP BY и выводе. |
| `partsupp` | `partkey`, `suppkey` | partkey связывает поставку с деталью; suppkey фильтруется через подзапрос supplier и участвует в count(DISTINCT suppkey). |
| `supplier` | `suppkey`, `comment` | Подзапрос выбирает ключи поставщиков, для которых comment LIKE '%Customer%Complaints%'; основной запрос исключает эти ключи через NOT IN. |

Имена колонок соответствуют коннектору TPC-H: `brand`, `suppkey`, `comment`. Q16 по Bronze — [sql/q16.sql](sql/q16.sql).

В `bronze.bench_gzip` и `bronze.bench_zstd` созданы одинаковые три таблицы из `tpch.sf1`: те же колонки, PARQUET, без партиций. На каждой копии выполнен Q16 с join, фильтрами и DISTINCT. Основной Bronze сохраняется.

После одного прогрева выполнено по пять замеров на кодек с чередованием порядка GZIP/ZSTD. В таблице указаны медиана и диапазон запусков. Время взято из `stats.elapsedTimeMillis` Trino и включает планирование и завершение запроса. Клиент использует `127.0.0.1`, чтобы избежать задержки IPv6 localhost. OS cache прогрет.

GZIP занимает 3 166 135 байт, ZSTD — 3 141 370 байт. ZSTD меньше примерно на 0.78%. Диапазоны времени перекрываются, а при предварительном запуске порядок медиан был обратным. На этом объёме устойчивого победителя по скорости определить не удалось.

## 6\. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Ответ |
| :---- | :---- |
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | При больших аналитических объёмах удобно хранить дешёвые независимые файлы в объектном хранилище и отдельно масштабировать вычисления. Iceberg добавляет табличную схему, атомарные изменения и snapshots, а SQL-движок использует их как таблицы. Один набор файлов могут читать разные инструменты через открытый каталог. Для небольших транзакционных приложений обычная PostgreSQL проще: sf1 в этой работе не требует lakehouse по объёму, он выбран для изучения архитектуры. |
| Как прошла schema evolution на Silver? | В silver.lakehouse.part_supplier добавил quality_note varchar и переименовал её в data_note. Все 118 274 строки сохранились, новое поле в них NULL. Список файлов и размеры до и после совпали: изменились metadata и схема, Parquet не переписан. Iceberg сохраняет field ID колонки при переименовании. Результат — results/schema-evolution.json. |
| Пример скрипта восстановления данных из снапшота (time travel) | Сохранил snapshot 3187102991790105271 таблицы silver.lakehouse.eligible_supplier; удалил suppkey=1. Текущее число строк стало 9995, чтение FOR VERSION AS OF старого snapshot вернуло 9996; после ALTER TABLE ... EXECUTE rollback_to_snapshot стало 9996. Исполняемый SQL в sql/04-time-travel.sql; результаты в results/time-travel.json. Старые файлы и snapshot не удалялись. |

Schema evolution:

```sql
ALTER TABLE silver.lakehouse.part_supplier ADD COLUMN quality_note varchar;
ALTER TABLE silver.lakehouse.part_supplier RENAME COLUMN quality_note TO data_note;
SELECT count(*) AS rows, count_if(data_note IS NULL) AS null_new_column
FROM silver.lakehouse.part_supplier;
-- 118274 строки, 118274 NULL; файлы данных сохранились.
```

Восстановление из snapshot:

```sql
-- Snapshot ID для текущей загрузки.
SELECT snapshot_id FROM silver.lakehouse."eligible_supplier$snapshots"
ORDER BY committed_at DESC;
SELECT count(*) FROM silver.lakehouse.eligible_supplier FOR VERSION AS OF 3187102991790105271;
ALTER TABLE silver.lakehouse.eligible_supplier EXECUTE rollback_to_snapshot(3187102991790105271);
SELECT count(*) FROM silver.lakehouse.eligible_supplier;
```

Опыт с удалением и восстановлением выполняет `python -X utf8 scripts/lab.py travel`. При новой загрузке snapshot ID будет другим: скрипт получает его из `$snapshots`. Откат восстанавливает данные таблицы, а резервное копирование S3 нужно отдельно.

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Причина выбора |
| :---- | :---- |
| Apache Superset 4.1.2 | Для Q16 нужна SQL-аналитика и просмотр результата, поэтому выбрал BI с SQL Lab и коннектором Trino. Он умеет читать Bronze и Gold через один SQL-движок, не требует копирования данных; подключение и дашборд можно воспроизвести через API. Spark полезнее для batch ETL, а здесь добавил бы отдельный движок и более сложную настройку ради табличной витрины. |

Скрипты развёртывания — сервис `superset` в [docker-compose.yml](docker-compose.yml), [Dockerfile](superset/Dockerfile), [init.sh](superset/init.sh) и [superset_config.py](superset/superset_config.py):

```powershell
docker compose --progress quiet up -d --build superset
python -X utf8 scripts/setup_superset.py
```

Подключение через REST API Superset — [scripts/setup_superset.py](scripts/setup_superset.py):

1. Выполнил `superset db upgrade`, создал локального admin и запустил `superset init`. Для работы с API получил token авторизации и CSRF token.
2. Создал connection **Lakehouse Bronze** с URI `trino://gleb@trino:8080/bronze` и **Lakehouse Gold** с URI `trino://gleb@trino:8080/gold`. Включил SQL Lab. Это внутренний адрес Docker network.
3. Через SQL Lab API `/api/v1/sqllab/execute/` выполнил запрос по физическим таблицам Bronze:

```sql
SELECT 'part' AS table_name, count(*) AS row_count FROM bronze.lakehouse.part
UNION ALL
SELECT 'partsupp', count(*) FROM bronze.lakehouse.partsupp
UNION ALL
SELECT 'supplier', count(*) FROM bronze.lakehouse.supplier;
```

Ответ Superset: `part = 200000`, `partsupp = 800000`, `supplier = 10000`. Запрос первых 10 строк `bronze.lakehouse.part` вернул partkey/brand/type/size; первая строка: partkey=1, Brand#13, PROMO BURNISHED COPPER, size=7.

4. Создал dataset `lakehouse.q16_supplier_counts` на connection Gold, chart типа **Table** с четырьмя колонками и сортировкой Q16, dashboard **«Практическая №1 — Мухин Глеб Дмитриевич — Q16»**. Лимит 50 000 строк вмещает весь результат; отображение разбито на страницы по 20 строк.
5. Через `/api/v1/chart/data` получены все 18 314 строк, совпадающие с CSV Trino. Ответы и ID объектов — [results/superset.json](results/superset.json).

Дашборд: [http://localhost:8088/superset/dashboard/mukhin-q16/](http://localhost:8088/superset/dashboard/mukhin-q16/). Логин — `admin`, пароль — `SUPERSET_ADMIN_PASSWORD` из `.env`. Bronze можно открыть в **SQL → SQL Lab → Lakehouse Bronze → lakehouse** и выполнить запрос выше.

## 7\. Выводы

Bronze хранит исходные данные, Silver — отфильтрованные связи, Gold — готовый результат Q16. Parquet хранит колонки, а Iceberg управляет схемой, изменениями таблиц и snapshots в S3. На sf1 ZSTD занял примерно на 0.78% меньше места, но диапазоны времени GZIP и ZSTD перекрылись, поэтому устойчивого преимущества скорости не получилось. Для небольших таблиц выбрал хранение без партиций; Superset читает Gold через Trino. После изменения схемы и восстановления snapshot результат Gold совпал с исходным Q16.
