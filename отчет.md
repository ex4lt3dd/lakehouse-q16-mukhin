Каждое решение ниже относится к варианту 4 и проверено на локальном Docker-стеке. Скрипты, SQL и фактические результаты приложены рядом с [README](README.md). ФИО указано в написании, предоставленном для VK Education.

## 1\. Вариант и масштаб

| Поле | Значение |
| :---- | :---- |
| ФИО (как в VK Education) | Мухин Глеб Дмитриевич |
| Вариант (запрос) | Вариант 4 — Q16 «Parts/Supplier Relationship» |
| Масштаб `sfN` | `sf1` на всех слоях и в обоих вариантах бенчмарка |
| Почему выбрал такой масштаб | Локальный Docker Engine имеет 16 CPU и около 7.38 GiB RAM; Trino ограничен heap 3 GiB. sf1 даёт 200 000 деталей, 800 000 связей и 10 000 поставщиков: достаточно для полного join, фильтров и DISTINCT, при этом стек и несколько копий Bronze помещаются на ноутбуке. За счёт проекции нужных колонок реальные файлы невелики; для выводов о больших объёмах потребовался бы отдельный эксперимент sf10/sf100. |

### Скрипты, которыми поднимал стек

Полный исполняемый конфиг — [docker-compose.yml](docker-compose.yml), конфиги каталогов — [catalog](catalog/), скрипт запуска — [scripts/start.ps1](scripts/start.ps1). ## 3\. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
| :---- | :---- | :---- |
| `part` | `partkey`, `brand`, `type`, `size` | partkey — join с partsupp; brand <> 'Brand#45'; type NOT LIKE 'MEDIUM POLISHED%'; size IN (49, 14, 23, 45, 19, 3, 36, 9). brand/type/size участвуют в GROUP BY и выводе. |
| `partsupp` | `partkey`, `suppkey` | partkey связывает поставку с деталью; suppkey фильтруется через подзапрос supplier и участвует в count(DISTINCT suppkey). |
| `supplier` | `suppkey`, `comment` | Подзапрос выбирает ключи поставщиков, для которых comment LIKE '%Customer%Complaints%'; основной запрос исключает эти ключи через NOT IN. |

Использованы имена коннектора TPC-H без префиксов (`brand`, `suppkey`, `comment`). Остальные таблицы TPC-H и варианты 1–3 в работу не включены. Исходный Q16 по Bronze — [sql/q16.sql](sql/q16.sql).

В таблицах «МБ» означает **MiB = байты / 1024²**; это активные файлы данных текущего snapshot, без служебных metadata и старых snapshots. Детальные измерения — [results/table-metrics.json](results/table-metrics.json).

## 5\. Тесты производительности

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
| :---- | :---- | :---- | :---- |
| GZIP | 0.401 с (медиана); 0.387–0.503 с | 3.019462 | В этом запуске медиана ниже, чем у ZSTD, но размер чуть больше. Разбросы перекрываются: на sf1 это не доказательство устойчивого преимущества скорости. |
| ZSTD | 0.452 с (медиана); 0.392–0.501 с | 2.995844 | Размер немного меньше GZIP; в финальном запуске медиана выше. Оставил ZSTD как стандарт для слоёв ради компактности и единого конфига, не заявляя превосходства по скорости. |

Для каждого кодека Bronze материализован заново из того же `tpch.sf1` в `bronze.bench_gzip` и `bronze.bench_zstd`: одинаковые три таблицы, колонки, формат PARQUET и отсутствие партиций. Основной Bronze сохранился, поэтому бенчмарк не ломает Silver/Gold. Полный Q16 с join, фильтрами и DISTINCT выполнен по этим копиям, а не по готовому Gold.

Методика: один прогрев на кодек, затем пять измерений на каждый, с чередованием порядка GZIP/ZSTD. В таблице показаны медиана и диапазон финальных запусков без других SQL-запросов. Время взято из серверного `stats.elapsedTimeMillis` Trino REST API; это полное серверное elapsed time, включая planning/finishing, а не только CPU или время оператора scan. Клиент обращается к `127.0.0.1`, чтобы не добавлять проверенную двухсекундную задержку неработающего IPv6 localhost. OS cache прогрет; холодный cache Windows/WSL не заявляется.

GZIP занимает 3 166 135 байт, ZSTD — 3 141 370 байт: выигрыш ZSTD по размеру около 0.78%. Скоростные диапазоны перекрываются, и при предварительном запуске порядок медиан был обратным, поэтому на таком небольшом наборе устойчивого победителя по скорости не определил. Выбор ZSTD для слоёв — компактность, общий конфиг и поддержка в выбранном Trino, а не утверждение, что он всегда быстрее.

Все query IDs, SQL и метрики сохранены в [results/queries.jsonl](results/queries.jsonl), финальные прогоны — [results/benchmark-runs.csv](results/benchmark-runs.csv), сводка и время записи — [results/benchmark.json](results/benchmark.json). Исполняемый бенчмарк — `python -X utf8 scripts/lab.py benchmark`; для повторных измерений уже созданных копий — `python -X utf8 scripts/lab.py benchmark --measure-only`.

## 6\. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
| :---- | :---- |
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | При больших аналитических объёмах удобно хранить дешёвые независимые файлы в объектном хранилище и отдельно масштабировать вычисления. Iceberg добавляет табличную схему, атомарные изменения и snapshots, а SQL-движок использует их как таблицы. Один набор файлов могут читать разные инструменты через открытый каталог. Для небольших транзакционных приложений обычная PostgreSQL проще: sf1 в этой работе не требует lakehouse по объёму, он выбран для изучения архитектуры. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | В silver.lakehouse.part_supplier добавил quality_note varchar и переименовал её в data_note. Все 118,274 старых строк доступны, новое поле в них NULL. Список файлов и размеры до/после полностью совпали: изменились metadata и схема, Parquet не переписан. Iceberg идентифицирует колонку по field ID, поэтому переименование не превращает её в другую колонку. Результат в results/schema-evolution.json. |
| Пример скрипта восстановления данных из снапшота (time travel) | Сохранил snapshot 3187102991790105271 таблицы silver.lakehouse.eligible_supplier; удалил suppkey=1. Текущее число строк стало 9995, чтение FOR VERSION AS OF старого snapshot вернуло 9996; после ALTER TABLE ... EXECUTE rollback_to_snapshot стало 9996. Исполняемый SQL в sql/04-time-travel.sql; результаты в results/time-travel.json. Старые файлы и snapshot не удалялись. |

Выполненный пример schema evolution:

```sql
ALTER TABLE silver.lakehouse.part_supplier ADD COLUMN quality_note varchar;
ALTER TABLE silver.lakehouse.part_supplier RENAME COLUMN quality_note TO data_note;
SELECT count(*) AS rows, count_if(data_note IS NULL) AS null_new_column
FROM silver.lakehouse.part_supplier;
-- Проверено: 118274 строки, 118274 NULL; файлы до/после совпали.
```

Скрипт time travel с фактическим snapshot ID:

```sql
-- Реальный snapshot из этого запуска; для новой загрузки получите свой ID.
SELECT snapshot_id FROM silver.lakehouse."eligible_supplier$snapshots"
ORDER BY committed_at DESC;
SELECT count(*) FROM silver.lakehouse.eligible_supplier FOR VERSION AS OF 3187102991790105271;
ALTER TABLE silver.lakehouse.eligible_supplier EXECUTE rollback_to_snapshot(3187102991790105271);
SELECT count(*) FROM silver.lakehouse.eligible_supplier;
```

Полный опыт с удалением, проверками и восстановлением выполняет `python -X utf8 scripts/lab.py travel`. Для другой загрузки нужно получить свой snapshot ID из `$snapshots`, а не переносить ID из этого запуска. Восстановление меняет состояние данных; это не универсальная отмена schema evolution и не замена резервному копированию S3.

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
| :---- | :---- |
| Apache Superset 4.1.2 | Для Q16 нужна SQL-аналитика и просмотр результата, поэтому выбрал BI с SQL Lab и коннектором Trino. Он умеет читать Bronze и Gold через один SQL-движок, не требует копирования данных; подключение и дашборд можно воспроизвести через API. Spark полезнее для batch ETL, а здесь добавил бы отдельный движок и более сложную настройку ради табличной витрины. |

Скрипты развёртывания — сервис `superset` в [docker-compose.yml](docker-compose.yml), [Dockerfile](superset/Dockerfile), [init.sh](superset/init.sh) и [superset_config.py](superset/superset_config.py):

```powershell
docker compose --progress quiet up -d --build superset
python -X utf8 scripts/setup_superset.py
```

**Выполненные действия в консоли через REST API Superset** ([scripts/setup_superset.py](scripts/setup_superset.py)):

1. После `superset db upgrade`, создания локального admin и `superset init` выполнил login и получил CSRF token; значения не сохранял в отчёт или Git.
2. Создал connection **Lakehouse Bronze** с URI `trino://gleb@trino:8080/bronze` и **Lakehouse Gold** с URI `trino://gleb@trino:8080/gold`. Включил SQL Lab. Это внутренний адрес Docker network.
3. Через SQL Lab API `/api/v1/sqllab/execute/` выполнил запрос по физическим таблицам Bronze:

```sql
SELECT 'part' AS table_name, count(*) AS row_count FROM bronze.lakehouse.part
UNION ALL
SELECT 'partsupp', count(*) FROM bronze.lakehouse.partsupp
UNION ALL
SELECT 'supplier', count(*) FROM bronze.lakehouse.supplier;
```

Ответ Superset: `part = 200000`, `partsupp = 800000`, `supplier = 10000`. Также прочитал первые 10 строк `bronze.lakehouse.part` с колонками partkey/brand/type/size; например partkey=1, Brand#13, PROMO BURNISHED COPPER, size=7. Это реальные данные Bronze, прочитанные через BI, а не пример ответа.
